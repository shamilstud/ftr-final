## Reading notes

Written by hand after checking the raw results of the 2026-11-06 runs. Causes marked as hypotheses were not tested.

- **Exp1.** Baseline graceful delete: outage 25.0-25.6 s although endpoints returned in 0.9-1.1 s; forced delete: 2.0 s. The cause of the long graceful outage is not established. The endterm's 23 s figure was cut short by its window. Improved: no failed request in 3 runs; one request failed over in the gateway log (`502, 200`).
- **Exp2.** The baseline's higher success during the outage (37 % vs 8 %) is not better availability: its requests wait up to the 12 s client timeout, so some finish after the restore. The gateway gives up within 10 s. After one timeout, `max_fails=1` marks both replicas down and later requests get a fast 503 (`502` from `no live upstreams`). That is the trade-off: faster, honest failure against fewer late successes. The API's own 500s pass through the gateway unchanged.
- **Exp3.** Baseline hypothesis failed: predicted 8-10 s per request, measured p50 10.0-18.0 s, max 34 s, 30 % failed. Failures are connections closed by the server without a response. Hypothesis: the API's 15 s `WriteTimeout`. Confounder: the client's write retries (1001, mostly 429 from the 60 creates/min route limit) add load on the baseline. The improved run's retries all succeeded, `504, 200`. Readiness did not remove the slow replica, as predicted, because `/health` does not touch the database. Improved recovery of 9.84 s in one run comes from one 235 ms request after the removal, just over the 200 ms threshold; the other two runs give 3.78 s and 1.42 s. ApiHighErrorRate fired in the improved runs, though clients saw no failure: the API records a request the gateway timed out as a 500.
- **Exp4.** Postgres logged `unexpected EOF on client connection with an open transaction` for the interrupted backends, and each retry was answered 201, so the first attempt really was rolled back. The baseline's retry time grew 3.6 -> 22.2 -> 34.1 s with restart count: kills about 44 s apart put the container into kubelet's restart back-off, so 3.6 s is the fair figure for a first crash. The idempotency and the transaction are in the application, so this does not separate the configs on data integrity, only on recovery time.
- **Exp5.** The baseline row fails because of the rate limiter, not capacity: API CPU stayed near 61 millicores. 1080 of 3600 requests got 429 once the 1200/min per-process limit ran out, 36-39 s into the step. The improved config avoids it only because each replica counts separately (900/min each), so its limit is effectively doubled, not shared. The 41 baseline connection errors appear only while the limiter is active; the cause is not established. Plan hypothesis that the baseline also holds this rate: failed.
- **Exp6.** Requests already in flight on the hung replica got a 503 after 5 s with a single try (`504`): 34 of 1076 in total, all within about 5 s of the fault, and no failover. Exp3's slow replica did fail over. Hypothesis: the difference is that readiness removed the hung replica from DNS while those requests were in flight, leaving nginx no other peer for them to try. A database outage fires ApiHighLatencyP95 as well as ApiHighErrorRate, which is correct: requests really were slow. Exp6 replica and error-rate gateway statistics were read from the gateway logs after the runs. In error-rate rep 2, the secondary alert's clear time was not recorded (fixed later; its primary alert was).
- **Exp7.** The 2 failed cases are one case in both repetitions: `B GET /api/households/{A}` expected 404, got 405, because the route has no GET. Nothing was disclosed, but the case tests routing, not tenant isolation; the expected value was my error and was left as written. The other cases show that tenant isolation is enforced. The two requests missing from the API log are the 3 MB bodies, which the gateway rejected with 413 first and logged.
- **Exp8.** As predicted, the baseline survived too: a default RollingUpdate with 1 replica keeps the old pod, so this result shows no gain from the improved config. Its bad pod takes longer to go (6.1-6.5 s vs 0.8-1.9 s) because of the preStop `sleep 5`. No alert noticed the stuck rollout in any run: a monitoring gap. The broken release's first run at a 256Mi Postgres limit was a real outage (3.61 % availability, Postgres OOM-killed) that disappeared at 1Gi. That supports memory pressure as the cause, on one run pair; it is excluded from this table and kept as evidence that the database is a single point of failure.
- **All.** One-node kind cluster on a laptop: replicas share one host, the load generator runs on it, and pod-level faults cannot show node failure. Repetitions are few (2-4), so ranges describe behaviour and are not statistical estimates.
